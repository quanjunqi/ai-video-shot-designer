## 一、交付门禁（强制流程 · 三层防线）

> 规则写进文件 ≠ 被执行。**代码层面的问题必须在写代码时拦截（L1/L2），不靠打开浏览器才发现（L3 仅兜底）**。
> 任何前端改动交付前必须完整执行，未通过必须修复后再交付，禁止凭记忆或"我改了代码应该没问题"跳过。

### L1 · 组件层根治（设计时消灭反模式）

- 公共基类一处改、全局生效：如 `SelectTrigger` 基类统一 `w-full min-w-0`（全局 45 处使用者免改）、grid 列容器统一 `min-w-0`。
- 新增组件时先对照反例库 R1-R9 设计，不从零引入旧模式。

### L2 · 静态门禁（强制命令 · 代码层检测，不靠浏览器）

- 交付前必须执行 `cd apps/web && npm run gate`（= 严格 typecheck `tsconfig.app.json` + eslint + `node scripts/quality-gate.mjs`）。
- `quality-gate.mjs` 静态扫描已知反模式：`||/&&` 与 `??` 同子句混用（R9·oxc 根因）、`SelectTrigger` 显式 `w-fit`（R2）、grid 列缺 `min-w-0`（R2）、纯图标按钮缺 title/aria-label（可访问性）、页面级 `max-w-xl/2xl`（R3）。
- **`GATE=0`（0 error、0 warning）是交付前置条件**；warnings 逐条核对，可修复即修复。
- eslint 严格模式暴露的遗留类型错误必须清零（曾因默认 tsc 宽松漏检，`tsconfig.app.json` 才是验收口径）。
- `||/&&` 与 `??` 的判定必须精确到**同一子句**：仅当两者之间无括号 / 逗号 / 分号 / `{` 模板插值分隔时才拦截；`(a||b) ?? c`、`a || (b ?? c)` 等括号隔离写法合法，不得误报（首版按「行内出现两者即报」误报 19 处，已精确化至全量扫描 0 误报）。
- R3 只拦 `max-w-xl/2xl`；`max-w-3xl`（768px，内容区合理上限）及 3xl+ 视为规范留白，不得误拦。

### L3 · 浏览器兜底（仅验证静态检测不到的事实）

- 静态规则覆盖不了的：布局最终渲染、真实请求链路、服务进程探活（`healthz`）、交互反馈文案。
- 此时才打开浏览器截图 + `getBoundingClientRect` 交叉检测 + 真实走交互。
- **禁止**：把本可在代码层拦截的问题（R2 溢出/重叠、R3 过窄、未用 import、类型错误）留到浏览器才发现。

### 六步硬门禁（L1→L3 合并为交付动作）

1. **重读本文件**：打开本文件（`.agents/skills/frontend-quality/rules.md`），逐条读 [自检清单](#九交付前自检清单清单-1-7) 与 [反例库](#十一反例库黑名单r1-r10)，不凭记忆。
2. **跑静态门禁**：`npm run gate`，GATE=0（typecheck + eslint + quality-gate 全绿），不绿不交付。
3. **核对反例模式**：对照 R1-R10，确认本次改动不命中任何黑名单模式（命中即视为门禁未通过）。
4. **打开涉及页面**：浏览器导航到本次改动的真实页面/弹窗/流程，确认路由可达、服务未挂（healthz 探活）。
5. **真实走一遍交互 + 截图矩形检测**：点击每个新入口（添加/编辑/删除/克隆/预览/测试…），确认有反馈、无死链、失败路径有真实文案；对弹窗/卡片内可点击元素跑 rect 交叉检测。
6. **登记反例**：新发现的问题类型 → 当日追加进 [反例库](#十一反例库黑名单r1-r10)（问题/根因/修复/预防项），闭环成黑名单。

### 门禁纪律（追加规则）

- 用户每纠正一个问题，在对应改动完成后**当日**在 [`lessons.md`](lessons.md) 登记一条（问题/根因/预防项），并登记固化成的规则编号。
- **每次交付前必须重读本文件并执行顶部「交付门禁」三层六步，逐项打勾；有未通过项必须修复后再交付。禁止凭记忆跳过门禁。**
- **`cd apps/web && npm run gate`（严格 typecheck + eslint + quality-gate 静态扫描）是任何前端交付的强制前置步骤，GATE=0 才可交付。** 代码层面可静态判定的问题一律在开发期拦截，不留给浏览器验收（反例 R10）。
- 浏览器验收（L3）只验证静态检测不到的事实：最终渲染、真实请求链路、服务探活、交互反馈。禁止用浏览器替静态门禁兜底。
- 本文件是 `.agents/skills/frontend-quality/` 下的规则库，随项目演进持续维护；`SKILL.md` 是执行时的快速参考。
- 反例库（R1-R10）是黑名单：交付时按模式自查，命中任一模式即视为门禁未通过。

## 二、代码逻辑自检（必做）

> 迭代自检 = 代码逻辑检查 + UI 视觉检查 + 数据持久化检查（依次对应本节代码逻辑 / §三 UI 视觉 / §五 数据持久化）。

### 2.1 构建验证

- [ ] 后端 `go build` 无错误
- [ ] 前端 `tsc --noEmit` 无错误（实际验收以 `npm run gate` 内的 `tsc -p tsconfig.app.json` 严格口径为准，禁止用默认宽松 tsc 代替）
- [ ] `cd apps/web && npm run gate` 达 `GATE=0`（typecheck + eslint + quality-gate 全绿）
- [ ] 无未使用的导入、变量、参数
- [ ] 注意：类型检查/构建通过 **≠** 自检通过 —— 涉及 React 组件改动时必须另有浏览器实际渲染验证（见 §八 R-HOOK-002、§一 L3）

### 2.2 数据流验证

- [ ] API 请求参数正确传递（检查协议模板 params role 定义）
- [ ] 响应结果正确提取（检查 responseParams 路径）
- [ ] 响应提取兜底：目标响应 key 命中 **null 或空串**时必须回退同结构的 `reasoning_content`（思考型/reasoning 模型会把 `choices.0.message.content` 置 null，全部输出落在 `reasoning_content`；回退需保留数组下标，非空即采用）——否则会把上游正常输出误判为「内容过短（可能被上游截断）」
- [ ] 状态更新完整（所有分支都更新状态，无遗漏）
- [ ] 本地 state 与 store 同步（如 viewing、editing 等）

### 2.3 边界条件

- [ ] 空数据状态（列表为空、字段为空）
- [ ] 加载中状态
- [ ] 失败状态（网络错误、API 错误、超时）
- [ ] 重复操作防护（防重复点击、防重复提交）

### 2.4 数据持久化

- [ ] 刷新页面后数据不丢失
- [ ] 切换页面后数据不丢失
- [ ] 多浏览器标签页数据一致
- [ ] 完整「修改 → 刷新 → 切换页面 → 返回」闭环验证见 §五 R-DATA-003（含服务端同步确认）

### 2.5 提交前代码逻辑检查

- [ ] CRUD 完整性（R-CRUD-001/002/003，见 §七）
- [ ] 状态机正确性（状态迁移、边界情况）
- [ ] 数据一致性（关联数据、级联删除）
- [ ] 错误处理（API 失败、网络异常、空数据）

### 2.6 数据创建纪律（防刷新重复 / 竞态）

- [ ] **禁止页面加载时自动创建业务数据**：自动提取 / 自动创建类 `useEffect` 必须移除，所有数据创建必须由用户明确操作（点击按钮）触发——否则后端数据尚未加载完（列表为空）时自动提取会抢跑创建，每次刷新都新增一批重复数据。
- [ ] **禁止用 `Date.now()` 作为业务 id**：去重必须使用稳定标识符（name / id）。
- [ ] 已存在对象必须用**已有 id 更新**（保留用户已填写的字段），新对象使用基于稳定标识符生成的 id（如 `${episodeId}-char-${name}`）；明确区分新增/更新数量。

## 三、UI 设计自检（必做，8 维度）

> 逐项自检；每个维度同时适用 §六「品质标准（Awwwards 级）」的基准要求（已并入本节，不再重复）。

### 3.1 排版（Typography）

> **Awwwards 基准（原文）**：字号阶梯（标题/正文/辅助/代码）是否成系统；行高、字距是否统一；**截图检查同行元素矩形是否相交**

- [ ] 字体大小层级清晰（标题/正文/辅助文字区分明确）
- [ ] 字号阶梯（标题/正文/辅助/代码）成系统；行高、字间距合理且统一
- [ ] 图片容器比例正确（与内容匹配，如角色立绘用竖版）
- [ ] 文字不溢出、不截断、不重叠
- [ ] **截图检查同行元素矩形是否相交**（rect 交叉检测：`ox > 0 && oy > 0` 即判定相交）

### 3.2 留白（Whitespace）

> **Awwwards 基准（原文）**：区块间距、卡片内边距是否形成节奏；是否存在"挤"或"空得无意义"；**容器是否写死 max-w 导致两侧大留白**

- [ ] 卡片内边距充足，内容不拥挤
- [ ] 元素之间间距有节奏感（不是均匀堆砌）；区块间距、卡片内边距形成节奏
- [ ] 重要区域有视觉呼吸空间
- [ ] 整体布局不压抑、不空洞；不存在"挤"或"空得无意义"
- [ ] **容器是否写死 `max-w` 导致两侧大留白**：内容区应撑满可用宽度，`max-w` 仅用于弹窗等窄场景（见 R3）

### 3.3 视觉层级（Visual Hierarchy）

> **Awwwards 基准（原文）**：主次信息是否一眼可辨（尺寸/字重/色/装饰）；操作按钮是否可预期；**关键信息（如生效规则全文）是否默认可见而非折叠**

- [ ] 主次分明（核心内容突出，辅助内容弱化）；主次信息一眼可辨（尺寸/字重/色/装饰）
- [ ] 状态标识清晰（成功/进行中/失败/未开始）
- [ ] 信息分组合理（相关内容聚合，无关内容分隔）
- [ ] 操作按钮可预期
- [ ] 无冗余代码（如多个条件分支只显示一个的情况）
- [ ] **关键信息（如生效规则全文）默认可见而非折叠**；折叠仅用于次要详情（见 R7）

### 3.4 色彩（Color）

> **Awwwards 基准（原文）**：用色是否克制统一；语义色（成功/危险/信息）是否一致；深浅模式是否都可用

- [ ] 主题色一致（全站统一主色调，无突兀颜色）；用色克制统一
- [ ] 状态色规范（成功=绿、警告=黄、错误=红、信息=蓝/中性）；语义色（成功/危险/信息）一致
- [ ] 对比度达标（文字与背景对比度 ≥ 4.5:1）
- [ ] 深色/浅色模式适配（如适用），深浅模式都可用
- [ ] 无硬编码颜色（使用 CSS 变量或 design token）

### 3.5 动效（Motion）

> **Awwwards 基准（原文）**：过渡时长/缓动是否统一（150-250ms）；是否避免廉价抖动；**loading/加载态是否有明确文案与图标**

- [ ] 加载动画有设计感（不是简单的转圈）
- [ ] 状态切换有过渡（淡入/淡出、滑动、缩放）
- [ ] 悬停反馈明确（hover 状态变化）
- [ ] 动画时长合理（200-400ms，不拖沓不突兀）；过渡时长/缓动统一（Awwwards 基准 150-250ms）——两档取齐后**同一页面内必须统一**
- [ ] 是否避免廉价抖动
- [ ] 尊重 `prefers-reduced-motion`（如适用）
- [ ] **loading / 加载态必须有明确文案与图标**

### 3.6 微交互（Micro-interactions）

> **Awwwards 基准（原文）**：按钮/开关/选择器是否有 hover/active/disabled 反馈；空态/加载态是否完整；**无内容占位（如「选择风格」）是否有默认值或明确引导**

- [ ] 按钮点击有即时反馈（视觉变化 + 操作结果）
- [ ] 按钮/开关/选择器有 hover / active / disabled 反馈（见 R-UI-003）
- [ ] 表单输入有校验反馈（实时/失焦）
- [ ] 操作成功/失败有 toast 或内联提示
- [ ] 空态/加载态是否完整（空状态必须有引导，见 R-UI-004）
- [ ] 无"假功能"按钮（点击后提示"开发中"的必须移除或禁用）
- [ ] 下拉选择、开关等控件状态变化有反馈
- [ ] **无内容占位（如「选择风格」）必须有默认值或明确引导**：任何有内容的区域打开即展示内容（如默认选中首个 enabled 项并直接图文展示），不允许出现空白占位 + 加载动画

### 3.7 响应式（Responsive）

> **Awwwards 基准（原文）**：窄屏是否无溢出、无挤压；网格是否降列；长文本是否可滚动；**grid 列内元素是否 min-w-0 + truncate，防内容撑宽挤出兄弟列**

- [ ] 移动端（< 768px）布局正常
- [ ] 平板端（768-1024px）布局正常
- [ ] 桌面端（> 1024px）布局正常
- [ ] 无固定宽度导致溢出（如 `grid-cols-[300px_1fr]`）
- [ ] 图片、视频等媒体自适应
- [ ] 弹窗、抽屉等在小屏幕上适配
- [ ] 窄屏无溢出、无挤压；网格按需降列；长文本可滚动
- [ ] **grid 列内元素是否 `min-w-0` + `truncate`，防内容撑宽挤出兄弟列**（见 R-UI-002 / R-UI-006 / 反例 R2）
- [ ] **三栏/多栏布局每一栏必须有独立滚动区**：固定标题栏（`shrink-0` + `border-b`）+ 独立内容滚动区（`min-h-0 flex-1 overflow-y-auto`）；禁止整个面板无滚动导致底部内容（如生成按钮、来源与版本）被截断；交付前逐栏确认可独立滚动到底部

### 3.8 原创性（Originality）

> **Awwwards 基准（原文）**：是否照搬通用后台模板感；是否有可识别的设计语言

- [ ] 设计有独特视觉识别点（不是通用模板、不是照搬通用后台模板感）
- [ ] 体现产品专业属性（如"漫剧导演工坊"的艺术感）
- [ ] 有可识别的设计语言
- [ ] 图标、插画等视觉元素统一风格
- [ ] 无抄袭或过度借鉴痕迹

## 四、UI 反模式规则库（R-UI-*）

> 规则编号永久不变，新增规则追加编号，不修改已有编号。所有 `R-UI-*` 均为**代码层可检测**（可扫描的已接入 `quality-gate.mjs`，标注「人工检查」的进入交付自检清单）。

### R-UI-001：侧栏/窄容器标题必须 `whitespace-nowrap`
- **触发场景**：宽度 < 400px 的容器内的标题（h2/h3/label）
- **反模式**：标题因容器太窄而竖排（"项目"在上，"设置"在下）
- **修复**：所有侧栏标题加 `whitespace-nowrap`
- **检测**：`grep -rn 'h2 className=' src/features/comic/ | grep -v 'whitespace-nowrap'`

### R-UI-002：多列布局在窄栏必须降级
- **触发场景**：侧栏（< 400px）内使用 `grid-cols-3` / `grid-cols-4`
- **反模式**：控件挤压、文字截断、按钮重合
- **修复**：侧栏内最多 `grid-cols-2`，筛选控件用 `flex-wrap`
- **检测**：`grep -rn 'grid-cols-[34]' src/features/comic/`

### R-UI-003：按钮/可点击元素必须有 hover 反馈
- **触发场景**：所有 `button`、可点击 `div`、`Link`
- **反模式**：hover 无视觉变化，用户不知道可点击
- **修复**：至少加 `hover:bg-*` 或 `hover:text-*` 或 `hover:scale-*`
- **检测**：人工检查（代码扫描难以覆盖）

### R-UI-004：空状态必须有引导
- **触发场景**：列表/网格无数据时
- **反模式**：只显示"暂无数据"，用户不知道下一步做什么
- **修复**：空状态 = 图标 + 说明文字 + 行动按钮（如"创建"、"进入工坊"）

### R-UI-005：可折叠组件必须有过渡动画
- **触发场景**：所有展开/折叠组件
- **反模式**：瞬间展开/折叠，视觉跳变
- **修复**：用 `grid-rows-[0fr]→grid-rows-[1fr]` 或 `max-height` 过渡

### R-UI-006：长文本必须防溢出
- **触发场景**：卡片标题、标签、下拉选项
- **反模式**：长文本溢出容器、破坏布局
- **修复**：`truncate` 或 `break-words` 或 `line-clamp-*`

## 五、数据持久化规则（R-DATA-*）

### R-DATA-001：用户可修改的设置字段必须同步服务端
- **触发场景**：项目设置、用户偏好、规则配置等用户可修改的字段
- **反模式**：只写本地 localStorage，刷新/切换页面后丢失
- **修复**：修改时调用 API 同步服务端；本地为乐观更新，API 失败回滚
- **验证**：修改 → 切换页面 → 返回 → 检查数据保留

### R-DATA-002：mergeServerProject 不得覆盖本地未同步的修改
- **触发场景**：从服务端加载项目数据时
- **反模式**：直接用服务端值覆盖本地字段
- **修复**：比较 updatedAt，本地更新则保留本地值；或前端修改时立即同步服务端

### R-DATA-003：数据修改必须验证完整闭环
- **触发场景**：所有涉及数据修改的功能
- **验证步骤**：
  1. 修改后立即显示正确（不报错）
  2. 刷新页面后数据保留
  3. 切换页面后返回数据保留
  4. （如适用）多标签页一致性

### 数据持久化检查清单

- [ ] 修改 → 刷新 → 读取闭环（R-DATA-003）
- [ ] 切换页面后数据保留（R-DATA-001）
- [ ] 服务端数据已同步（检查数据库或 API 返回）

## 七、CRUD 完整性规则（R-CRUD-*）

### R-CRUD-001：列表页必须支持删除（单选/多选/全选）
- **触发场景**：所有列表页（项目、渠道、模型、协议、资产等）
- **反模式**：只有创建，没有删除入口
- **修复**：列表页必须有：单项删除按钮 + 多选 checkbox + 全选 + 批量删除

### R-CRUD-002：所有配置项必须支持编辑
- **触发场景**：渠道、模型、协议、规则等配置项
- **反模式**：只能创建不能修改
- **修复**：每个配置项必须有编辑入口，编辑后保存生效

### R-CRUD-003：敏感信息不得明文展示
- **触发场景**：API Key、令牌、密码等
- **反模式**：在列表/卡片上明文展示 API Key
- **修复**：列表上只显示掩码（如 `sk-****abcd`），编辑页有"小眼睛"切换显示

## 八、React Hooks 规则（R-HOOK-*）

> 运行时错误，类型检查无法捕获。

### R-HOOK-001：useState/useEffect 等 Hooks 必须在组件顶层调用，禁止在早期 return 之后
- **触发场景**：组件中有条件渲染（`if (!data) return <Empty />`），在条件分支后新增 Hooks
- **反模式**：`if (!interp) return (...)` 之后写 `const [showNotes, setShowNotes] = useState(false)`
- **错误表现**：`Rendered more hooks than during the previous render`，页面白屏
- **修复**：所有 Hooks 必须放在组件函数体最顶层、任何早期 return 之前
- **检测**：
  ```bash
  # 检测 if (...) return 之后是否有 useState/useEffect/useMemo/useCallback
  # 人工审查：每个组件的 Hooks 是否都在第一个 return 之前
  grep -n 'useState\|useEffect\|useMemo\|useCallback' src/features/comic/*.tsx | head -20
  ```
- **工具**：项目应配置 `eslint-plugin-react-hooks`，`rules-of-hooks` 规则可在代码阶段捕获此错误

### R-HOOK-002：自迭代检必须包含浏览器渲染验证，不能只靠类型检查
- **触发场景**：任何涉及 React 组件修改的任务
- **反模式**：只运行 `tsc --noEmit` 就宣称"自检通过"
- **修复**：自迭代检清单必须包含"浏览器实际渲染验证"项，修改组件后必须在浏览器中打开对应页面确认无运行时错误
- **检测**：自检报告中必须有浏览器截图或页面文本验证记录

## 九、交付前自检清单（清单 1-7）

> 这份清单是交付动作的逐项打勾口径，被 [`lessons.md`](lessons.md) 教训条目的「预防检查项」按编号引用（清单 1-7），**编号不得变更**。

### 1. CRUD 四态闭环
- [ ] 新增的对象，是否同时提供了 **查询 / 编辑 / 删除** 入口？（批量删除、多选、全选是否合理存在）
- [ ] 删除是否有确认、是否可恢复（软删除/本地移除），删除后刷新是否会"复活"？
- [ ] 编辑是否开放全部应开放字段（内置对象也要能编辑，不能只锁死）？
- [ ] 是否支持**复制/克隆**（相同配置快速复制改少量内容）？

### 2. 布局与溢出
- [ ] 弹窗/卡片内控件是否**同行重叠**（grid 列是否生效、Select 是否撑满整行挤压兄弟控件）？
- [ ] 长文本/长 URL/长名称是否溢出（换行、省略、可滚动）？
- [ ] 按钮数量增多后排版是否被挤压（操作按钮应沉底或成组）？
- [ ] 内容过多时输入区/列表是否可滚动、可到达底部按钮？
- [ ] 三栏/多栏布局每栏是否有独立滚动区（`min-h-0 flex-1 overflow-y-auto`），底部内容是否被截断？（详见 §3.7）

### 3. 错误与提示
- [ ] 失败文案是否**真实透传**根因（禁止 catch 后写死误导性文案）？
- [ ] 后端不可达时是否区分"服务挂了"与"业务失败"？
- [ ] 新对象类型（自定义/内置）在探测、读取等所有路径都被覆盖，不能只支持平台内置？

### 4. 数据安全
- [ ] API Key / 令牌是否**不出现在卡片/列表**，只在编辑弹窗内查看明文（小眼睛）且可改？
- [ ] 密钥是否加密存储（只写不读，主动查看才解密）？

### 5. 规则与配置
- [ ] 规则是否**先定义、后生效**（规则中心定义 → 项目选择生效，而不是在项目内改规则）？
- [ ] 配置是否可随时修改（模型/视觉风格/规则）？修改后是否即时生效？

### 6. 专业性与语义
- [ ] 拆解/分段是否按**语义格式**（场次/章节标记），不按字符数机械切分？
- [ ] 摘要/解读是**分析结论**而不是原文搬运？
- [ ] 对象下限/上限是否合理（不要随意设置不必要的下限）？

### 7. 验证与交付
- [ ] typecheck / build 是否通过？
- [ ] 浏览器**实测**过真实交互路径 + 截图确认渲染（不是只看代码）？
- [ ] 本地服务是否可达（后端没挂、代理正确）？
- [ ] 测试数据是否清理（副本/测试 key/脏 localStorage 还原）？
- [ ] **清理前必须确认对象为本次测试自建**：核对创建时间 / 命名前缀 / id 白名单，禁止按模糊条件批量删；用户创建的渠道、模型、凭据一律保留（用户 Key 加密存储不可恢复，删错无法补救）
- [ ] 用户级数据是否持久化到后端租户域（禁止只写 localStorage 的"假入库"；平台共享目录只读防污染）？
