# 需求验收清单

> 模板见 `templates/acceptance-checklist.md`（本目录）。本文件是 AI 执行时的快速参考。
> 与 `frontend-coding` / `backend-coding` / `frontend-quality` 互补：本 skill 管「需求到验收的追溯链」，编码规范管「怎么写」。

## 什么时候加载这个 skill

- 任何开发任务开工前（必须）：先产出验收清单，再写代码
- 开发完成、提交 PR 前（必须）：按清单逐项自检勾对
- 收到需求但范围/验收标准不明确时：先补清单，再向用户确认

## 核心规则速查

| 编号 | 规则 | 检测方式 |
|---|---|---|
| AC-001 | 开工前必须产出验收清单（需求点逐条可验证） | 代码审查 |
| AC-002 | 清单每项有客观判据（判据/对象/时点/例外 四要素） | 审查 |
| AC-003 | 设计稿/高保真稿逐点映射到需求点（防理解偏差） | 审查 |
| AC-004 | 开发完成后逐项自检勾对，未过项不得交付 | 审查 |
| AC-005 | PR 必须附勾对结果（通过项/未过项/原因） | PR 审查 |
| AC-006 | 三态（loading/error/empty）与边界逐项过 | 审查 |
| AC-007 | 反模式速查逐条自查（FE-*/BE-* 命中即改） | GATE + 审查 |
| AC-008 | 清单必须落成文件：`.github/tasks/<TASK-ID>-acceptance.md`（与任务卡同目录；无任务卡时用 `<日期>-<简述>-acceptance.md`） | 文件存在 |

## 强制流程（每次开发）

```
需求 → 1. 产验收清单（复制 templates/ → `.github/tasks/<TASK-ID>-acceptance.md`）
      → 2. 对照设计稿逐点映射（设计稿每个模块都有需求来源）
      → 3. 开发（按编码规范写）
      → 4. 自检勾对（清单逐项：过/未过/原因）
      → 5. GATE + 测试
      → 6. PR 附勾对结果
```

> 6 步缺一不可。**未产出清单 = 不得开工；未勾对 = 不得开 PR。**

## 禁止事项

- ❌ 跳过清单直接写代码
- ❌ 清单项写成模糊话术（"体验好""界面美观"）——必须可验证
- ❌ 自检勾对"全过"但 GATE 不绿 / 测试不过（判据造假）
- ❌ PR 不附勾对结果
- ❌ 用「验收靠人」替代清单——清单让 Owner 只需抽查
