# 为什么是 6 个微服务？

> 不是为了"微服务而微服务"，是每个服务拥有一类独立事实，变更节奏和扩容需求不同。

## 一句话

**一个服务拥有一类事实，其他服务通过契约访问，不直接跨库读写。**

## 为什么不分在一个服务里？

| 服务 | 拥有的数据 | 为什么独立 |
|---|---|---|
| workspace | 成员、授权、渠道凭据 | 安全敏感：密钥加密、租户隔离、审计要求高；和业务数据完全不同的变更节奏 |
| production | 项目、剧集、分镜、模型目录 | 业务核心：读写频繁、和前端交互多；不执行 AI 调用，不需要高并发 worker |
| execution | Job、Attempt、审计日志、用量 | 计算密集：需要 worker 池、限流、重试；不直接改项目数据 |
| asset | 上传文件、媒体元数据 | IO 密集：大文件上传、缩略图转码；和业务逻辑完全解耦 |
| web-bff | 无状态聚合层 | 前端唯一入口，薄转发；不需要自己的数据库 |
| outbox-relay | 事务性消息投递 | 基础设施：监听 outbox 表、投递事件；和业务服务解耦 |

## 好处

- **独立部署**：前端改了不需要重启 AI 网关
- **独立扩缩**：execution 可以根据 AI 调用量独立扩容
- **故障隔离**：一个服务挂了不影响其他
- **安全边界**：密钥只在 workspace，其他服务拿不到明文

## 什么时候该合并？

如果你发现两个服务总是同时改、同时部署、一起扩容，那可能是时候合并了。
目前这 6 个服务的边界是 ADR-001 确认的，合并需要新 ADR。
