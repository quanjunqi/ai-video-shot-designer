# ADR-005：设置中心信息架构（IA）重设计

- **状态**：提议（待 Owner 确认 §9）
- **日期**：2026-10-10
- **相关**：ADR-003（路由层）、ADR-004（中转站与供给池）、`docs/FRONTEND_QUALITY_GATE.md`

---

## 1. 背景：为什么必须重做，而不是继续加页面

Owner 反馈："修改的内容和设计的方案偏差太多，产品 UI 太混乱，功能也很复杂。"

**实测证据**（改造前的设置中心）：

| 导航项 | 页面行数 | 交互容器数（Collapsible/Tabs/Dialog/Sheet） |
|---|---|---|
| 渠道配置 | 516 | 19 |
| **协议配置** | 407 | **30** |
| **模型配置** | **798** | **34** |
| 调用审计 | 233 | 0 |
| 通用设置 | 120 | 0 |
| **逻辑模型管理** | 591（+ 候选面板 483） | 15 |

概念密度：`模型` 118 次 · `渠道` 56 · `协议` 43 · `逻辑模型` 32 · `候选` 31 · `目录` 26 · `凭据` 13 · `优先级` 11。

### 根因（三条，第一条是设计方的错）

1. **把数据库分层当成了界面分层**。ADR-003/004 定义的是**数据架构**（供给池 → 产品面 → 执行候选）。
   实现时却按这层建页面，于是把一条完整链路平铺成 4 个平级导航：
   `渠道配置 → 协议配置 → 模型配置 → 逻辑模型管理`。
   用户想"加一个模型"，必须先学会我们的内部数据模型。
2. **没有渐进披露**。一个页面 34 个交互容器 = 表单倾泻。接一个渠道的真实步骤有 8 步
   （base_url → 凭据 → 协议模板 → 请求参数映射 → 响应字段映射 → 目录行 → 候选绑定 → 优先级），
   全部平铺给用户。
3. **术语未业务化**。`逻辑模型`/`候选`/`协议模板`/`供给池`/`目录` 都是内部词汇。

**关键区分（本 ADR 的核心）**：
> **数据分层 ≠ 界面分层。** 分层数据架构应当保留（ADR-004 不变），
> 但**哪一层出现在界面上**是独立的设计问题。

---

## 2. 决策

### D1：一套界面，按「角色」控制深度，不按「用户类型」分两套

Owner 明确"可能个人也可能团队"。**不分两套界面**，理由：
个人创作者明天可能变成团队；团队成员也都是个人；分两套 = 双倍维护 + 用户不知道属于哪套。

**差异只体现在内容与权限**：

| | 个人创作者 | 团队 / 管理员 |
|---|---|---|
| 导航结构 | **完全相同** | **完全相同** |
| 「渠道」 | 只看**我的渠道** + 接入向导 | 增加：健康、最近同步、凭据轮换、**平台渠道**分组 |
| 「用量」 | 只看自己的消耗 | 增加：按成员、按项目 |

**导航项数不随用户类型变化** —— 会变的东西用户记不住。

### D2：导航固定 4 项

```
设置
├── 模型    ← 日常最高频：能用的能力（我们策展过的产品面）
├── 渠道    ← 接入来源（个人与团队都需要的刚需）
├── 用量    ← 治理：成本 / 失败与重试 / 审计明细
└── 偏好    ← 含「专家模式」总开关
```

> 修正记录：初稿曾建议"若以个人为主则把「渠道」折入「模型」详情、导航留 3 项"。
> **该判断偏轻** —— 个人用户也要接自己的 key，"接入我的渠道"是**刚需**，应保留一级导航。

### D3：术语业务化（UI 中禁止出现的词）

| 内部词 | UI 用词 |
|---|---|
| 逻辑模型 `logical_model` | **模型** |
| 候选 / 绑定 / `route_priority` | **渠道** + **顺序**（拖拽，不显示数字） |
| 协议模板 / 参数映射 / 响应映射 | **接入方式**（默认自动，不出现选择器） |
| `model_catalog` / 供给池 / 目录 | **不出现** |
| `ID_IMMUTABLE` / `MODEL_ALREADY_BOUND` | 翻译为"模型名不可改" / "已被别的模型占用" |

### D4：供给池的可见性规则（**不变量**）

供给池（`channel_models`）是**机舱，不是驾驶舱**。它的价值是三条**内部**能力：
一键接入（不必手建 92 行）· 策展有据（不漏新模型）· 变化可见（新增/下架/涨价）——
**一条都不需要用户看见它**。

但它必须在**两个地方**出现：

| 场景 | 为什么 |
|---|---|
| **接入向导第 2–3 步** | 用户此刻的任务**就是**"从这家能提供的东西里挑要用的" |
| **用户自己渠道的详情** | 那是**他自己的资源**，有权知道"我这家能调什么" |

**平台供给池与用户渠道的不对称（关键）**：

| | 平台供给池（我们接的 PearAPI 等） | 用户自己的渠道 |
|---|---|---|
| 全量展示给用户 | ❌ **不要** —— 92 个模型是噪音 | ✅ **要** —— 是他的资源 |
| 出现在哪 | 只在接入向导（我们内部策展用） | 渠道详情，常驻 |
| 用户看到的词 | **模型**（能力） | **我这家能调的模型** |

### D5：接入向导 —— 8 步收敛为 3 步

```
第 1 步  地址 + Key                        [测试连接]
第 2 步  系统自动：探测类型 → 同步模型清单 → 匹配内置协议模板 → 识别可用能力
         展示「发现 92 个模型，自动识别 6 类端点」
第 3 步  勾选要启用的模型 → 归到哪个「模型」
完成     协议模板 / 参数映射 / 响应映射**全部自动**
         └─ 仅当用户点「我要自定义接入」才展开
```

**专业能力体现在"系统认识这家上游并自动配对"，而不是"用户会填映射表"。**

### D6：渐进披露 + 专家模式

- 默认只露 **90% 用户都需要的**字段
- 「高级」（就地折叠）：重试、超时、优先级
- 「专家模式」（偏好里一个总开关）：协议/映射/原始响应体/批量操作
- **一套界面同时服务两类人**，而不是两套界面

### D7：专业能力长在**创作流**里，不长在设置里

这条回应 Owner 的第二个目标（"保证我们提供的专业能力"）。专业能力若藏在设置页，
它看起来像"配置项"而不是"能力"。三条具体做法：

| 做法 | 说明 |
|---|---|
| **能力 = 预设，不是选项** | 镜头语言/风格库以**一键套用**出现在创作界面（分镜/生成/画布节点）；设置里只管理"团队共享的预设库" |
| **能力在模型详情里可见** | 展示 `capabilities`：`支持参考图 · 首尾帧 · 4–30 秒 · 480P/720P · 最多 9 张参考` —— **这才是专业能力的载体** |
| **能力在选型时可被感知** | `StageModelPicker` 不只列名字，显示"✓参考图 ✓首尾帧 ⚠最长10秒"，选型时就知道能不能干这活 |

## 3. 现有页面的迁移方案

| 现有 | 行数/容器 | 去向 |
|---|---|---|
| 模型配置 | 798 / 34 | **拆**：模型定义 → 「模型」详情；参数/响应映射 → 向导「高级」；技术字段 → 专家模式 |
| 逻辑模型管理 + 候选面板 | 591+483 / 15 | **改名「模型」+ 升为主界面**；候选绑定 → 详情内「渠道与顺序」区段（**拖拽排序**） |
| 渠道配置 | 516 / 19 | 保留为「渠道」；**主入口改向导**；凭据/健康/同步留在列表与详情 |
| 协议配置 | 407 / 30 | **取消一级导航** → 降为向导「高级」折叠区（专家模式才显眼） |
| 调用审计 | 233 / 0 | 并入「用量」，与成本合并 |
| 通用设置 | 120 / 0 | 保留为「偏好」，新增「专家模式」开关 |

## 4. 非目标

- ❌ 不改 ADR-003/004 的数据架构（**供给池、候选、路由层都保留**）
- ❌ 不做多语言、多主题
- ❌ 不引入新的 UI 组件库（沿用现有 `components/ui/*`）
- ❌ 不在本 ADR 覆盖「任务中心」的展示改造（见 `TASK-OBS-001`）

---

## 5. 可验证的验收标准（怎么判断真的变好了）

| 指标 | 改造前 | 目标 |
|---|---|---|
| 一级导航项数 | 6 | **4** |
| 单页交互容器上限 | 34 | **≤ 8** |
| 最大页面行数 | 798 | **≤ 300** |
| 用户需理解的内部词数 | ≥ 6 | **3**（模型 / 渠道 / 顺序） |
| 接入新渠道步数 | 8（跨 3 页） | **3**（其中 1 步全自动） |
| UI 中出现的内部词 | 逻辑模型/候选/协议模板/目录 | **0** |

## 6. 风险

| 风险 | 缓解 |
|---|---|
| 重构期间两套界面并存导致混乱 | **先合并/降级旧页面，再上新功能**；不做长期双轨 |
| 砍掉「协议配置」一级导航会让高级用户找不到 | 向导「高级」+ 专家模式总开关；并在迁移说明中告知路径变化 |
| 角色权限差异引入分支复杂度 | 权限只控制**内容可见性**，不改结构与路由 |
| 拖拽排序在触屏/无障碍上不友好 | 提供键盘可用的"上移/下移"作为等价操作 |
| 与既有 `useSettingsStore`（zustand persist）冲突 | 服务端拥有的数据**不进 persist store**（已有先例：逻辑模型直连 `api.*`） |

---

## 7. 实施顺序（先减后加）

1. **合并/降级**：协议配置 → 向导高级；模型配置 → 拆入「模型」详情
2. **改向导**：渠道接入 8 步 → 3 步（含自动同步与模板匹配）
3. **改导航与命名**：6 项 → 4 项；「逻辑模型管理」→「模型」
4. **加专家模式开关**
5. **最后**才做 ADR-003 第 4/5 步的新页面（目录快照候选、租户策略）

---

## 8. 流程规则（建议写入 `AGENTS.md`）

> **任何涉及界面的工作，先出 IA / 线框（可 1 页），确认后才写代码。**

理由：CI 门禁只能保证"不退化"（typecheck/lint/覆盖率），**保证不了"结构正确"**。
本次设置中心的混乱正是"每个切片都过门禁、整体却失衡"的结果。
