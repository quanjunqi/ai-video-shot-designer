# ADR-001: 模型聚合网关架构 — 增强 execution 而非新建服务

## 状态

- **状态**：已接受
- **日期**：2026-10-10
- **决策者**：项目 Owner
- **相关 ADR**：无

---

## 背景

项目需要支持三类 AI 后端：
1. 中转站 API（如 PearAPI）
2. 官方 API（如 OpenAI、MiniMax）
3. 本地/云端部署的 ComfyUI

同时需要满足可审计、可治理的企业级要求。

面临的问题：
- 是否需要新建一个独立的"模型网关服务"？
- 还是在现有服务上增强？

约束条件：
- 项目已有 6 个微服务，不宜过度拆分
- execution 服务已经负责 Job 调度和 AI 调用
- 遵循项目架构规范"一个服务拥有一类事实"

---

## 决策

**我们决定：不新建独立网关服务，在 execution-service 上增强为模型聚合治理网关。**

具体措施：
1. 在 execution 服务内实现网关拦截层（认证、限流、审计、预算）
2. 三类执行器统一接口：API Connector / ComfyUI Agent / Cloud Runner
3. 模型定义仍在 production(Catalog)，execution 运行时锁定快照
4. 审计日志表 `gateway_audit_logs` 建在 execution 数据库

---

## 备选方案

### 方案 A：新建独立模型网关服务

**描述**：新建 `model-gateway` 服务，作为所有 AI 调用的统一入口。

**优点**：
- 职责单一，符合微服务理念
- 可独立部署和扩展
- 不影响现有服务

**缺点**：
- 增加运维复杂度（第 7 个服务）
- 增加网络跳数和延迟
- 与 execution 的 Job 调度职责重叠
- 需要跨服务事务（审计日志与 Job 创建）
- 项目当前阶段不需要这种粒度的拆分

**结论**：不选，因为过度拆分，增加复杂度而收益有限。

### 方案 B：在 BFF 层实现网关

**描述**：在 web-bff 服务中实现模型网关能力。

**优点**：
- 前端调用路径短
- 无需新增服务

**缺点**：
- BFF 是无状态的聚合层，不应持有业务数据
- 审计日志、用量记录需要持久化，不适合 BFF
- BFF 不应直接调用外部 AI API，应通过 execution
- 违反"BFF 无领域权威库"的架构原则

**结论**：不选，因为违反服务边界原则。

---

## 决策理由

1. **职责自然延伸**：execution 已经负责 Job/Attempt/预算/外部任务映射，网关是其自然延伸
2. **事务一致性**：审计日志与 Job 创建可以同事务，避免跨服务事务复杂度
3. **符合项目规范**：项目架构文档明确 execution 负责"供应商接入层"
4. **控制面与数据面**：Catalog(定义) 在 production，Execution(计划) 在 execution，符合"Catalog 管定义，Execution 锁定计划"原则
5. **渐进式增强**：可以在现有服务上逐步增强网关能力，不需要大重构

---

## 后果

### 正面影响

- 无需新增服务，运维简单
- 审计日志与 Job 同事务，数据一致性好
- 网络跳数少，延迟低
- 符合项目现有架构规范

### 负面影响

- execution 服务职责变重，需要注意内聚性
- 网关能力与 Job 调度耦合，未来如需独立扩展可能需要拆分
