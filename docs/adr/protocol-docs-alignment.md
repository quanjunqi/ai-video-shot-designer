# ADR-008：协议配置保留为「上游文档镜像 + 契约核对基准」
- **编号**：008

- **状态**：**已接受**（Owner 2026-10-10 勾选 §8 全部 6 条）
- **日期**：2026-10-10
- **相关**：ADR-003（路由层）、ADR-004（供给池）、ADR-005（设置中心 IA）、**ADR-007（本 ADR 修订它）**
- **触发**：Owner 提出「协议配置可以保留；它和开发文档是一回事，能不能和官网/云端/中转站的开发文档对齐」
- **编号说明**：为不覆写已写下的决策，本次以**新 ADR 修订 ADR-007**，而非改写 007 正文。
  ADR-007 状态建议由「提议」改为「**部分被 ADR-008 修订**」。

---

## 1. 修订什么

ADR-007 §1 的结论是：

| | 是否需要 |
|---|---|
| 「把不同上游 HTTP 形状统一起来」这个能力 | ✅ 必须保留 |
| **「用户可编辑的协议配置页面 + 表」** | ❌ **不需要** —— 这是我们的过度设计 |

**ADR-007 否定的是「让用户从零手写协议」，而不是"协议定义本身"。**
本 ADR 把被否定的那一半说法收敛为一句更准的话：

| | 修订后 |
|---|---|
| 「把不同上游 HTTP 形状统一起来」的能力 | ✅ **保留**（ADR-007 原结论不变） |
| 「用户从零手写协议」的界面 | ❌ **不需要**（ADR-007 原结论不变） |
| **「协议定义 + 它与上游开发文档的对齐关系」** | ✅ **保留，并从"配置项"升级为"资产"** |
| 协议配置页的定位 | 由「用户要学的配置表单」→ **「我们与上游之间的合同存档 + 契约核对基准」** |

**一句话**：它的价值不在**编辑**，在**对齐与核对**。

---

## 2. 为什么（三条理由）

1. **把负担变成资产**：当前协议配置被当作"过度设计"（407 行 / 30 交互容器）。
   定位为**上游文档的结构化镜像**后，它成为可查、可核对、可传承的知识库。
2. **它补上了「契约核对」缺的那块**：
   本项目**没有契约核对能力**（上游改了状态值/字段/端点，只能靠客户报障）。
   而"核对"必须有"**应该是什么**"的基准 —— 那个基准就是**上游开发文档**。
   ⇒ 文档对齐不是附属功能，**它是契约核对的前提**。
3. **它能防止已经踩过的坑**：`pt_builtin_minimax_video` 的完成/失败值写成
   迁移 008 曾写 `Success`/`Failed`；030 依**国际站**文档改成 `completed`/`failed`；
   而**我们实际轮询的端点**（`pt_builtin_minimax_video.pollPath = /v1/query/video_generation`，legacy）
   官方文档写的是 `Success` / `Fail` ⇒ **同一产品、不同文档页给出不同枚举**。
   若录入时必须标注「**对应文档哪一节、哪一版、何时核对**」，该错误在**录入当时**就会被发现。

---

## 3. ⚠️ 核心约束：**文档是线索，实测才是事实**

**不得"以文档为准"。** 本项目已实测到两个反例：

| 反例 | 事实 |
|---|---|
| 1 | **同一产品的不同文档页给出互相冲突的枚举**：我们轮询的 legacy 端点
（`/v1/query/video_generation`）文档写 `Success`/`Fail`；国际站另一套写 `completed`/`failed`。
⇒ 迁移 008 取 `Success`/`Failed`（半对：`Fail` 写成了 `Failed`），030 又依据另一页改成
`completed`/`failed`（对本端点可能**都不匹配**）。**照任何一页取值都可能与实际端点不符。** |
| 2 ✅ | **同一家文档里有互相矛盾的两套枚举**：MiniMax 顶层 `status` = `queued/in_progress/completed/failed`；另一套接口嵌套 `task.status` = `queued/running/succeeded/failed/cancelled`。**光看文档分不清该用哪个**，要靠"我们实际轮询的是哪个字段"判断 |

⇒ 因此协议定义必须**两类证据并列**，而非文档覆盖实测：

```
docRef            ← 文档依据（外部输入，可能过期或本身有误）
observedEvidence  ← 实测证据（我们自己跑出来的，是事实）
```

### 3.1 `docRef` 建议字段

| 字段 | 说明 |
|---|---|
| `source` | `official` / `cloud` / `relay`（中转站） |
| `url` | 文档链接（用于界面跳转与人工复核） |
| `docVersion` / `verifiedAt` | 照哪一版核对过、**何时**核对（没有日期就无法判断"还算不算数"） |
| `sections` | 提交端点 / 查询端点分别对应文档哪一节（**尤其两者不对称时**） |
| `authDoc` | 文档写的鉴权头与前缀（对应已有 `auth_header`/`auth_prefix`） |
| `statusEnumDoc` | **文档原文列出的**进行中 / 完成 / 失败值 |
| `referenceRuleDoc` | 文档写的参考图/视频/音频数量与时长限制（对应 ADR-007 参考实现的 `referenceRule`） |

### 3.2 `observedEvidence` 建议字段

| 字段 | 说明 |
|---|---|
| `lastProbedAt` | 最近一次实测时间 |
| `observedStatusCodes` | 实际观察到的 HTTP 状态码（含 401/403/404 的区分） |
| `observedStatusEnum` | 实际观察到的终态字面量 |
| `observedEndpoints` | 实际可用的提交/查询端点 |
| `discrepancies[]` | **文档与实测的差异清单**（差异本身要保留并可见，不是被抹平） |

### 3.3 冲突解决规则

> **以 `observedEvidence` 为准；差异必须保留并可见。**
> 差异本身就是「上游文档与实际不一致」的记录，是上游变更检测的信号来源。

---

## 4. 可见性与编辑权限

| 对象 | 权限 |
|---|---|
| **内置协议定义** | **只读**。取消"从零手写协议"的界面（ADR-007 原结论） |
| **用户对自己接入的渠道 / 中转站** | 可**补充覆盖与备注**（因为其文档可能与我们的内置不同） |

**覆盖是附加层，不修改内置定义**；一旦某租户覆盖，界面须显式标注「**已被本工作区覆盖**」，
避免出现"标着内置却已被改过"的假状态。

---

## 5. 巡检模式（Owner 已确认：**做成可巡检**）

对齐关系**会腐坏**（文档会改、上游会改）。因此必须可巡检，而非一次性录入。

### 5.1 两类巡检

| 类型 | 做什么 | 成本 | 频率建议 |
|---|---|---|---|
| **文档巡检** | 抓取上游文档，比对标出的端点 / 鉴权 / 状态枚举 / 参考图规则是否变化 | 0（仅网络） | 低频（如每周） |
| **实测巡检** | 对渠道做**零成本探测**（连通 + 鉴权观测 + 轮询端点可达），比对 `observedEvidence` | **0** | 高频（如每日） |

### 5.2 与「视频不做真实生成」约束的关系

本项目的既有约束是：**文本/图片可接受真实最小生成；视频不接受真实测试**。
⇒ 因此巡检**默认只做零成本探测与契约核对**；真实生成仅用于**接入时的分级验证**，
且视频的真实生成**必须由 Owner 显式付费授权**（默认不发生）。

### 5.3 巡检结果

产出**差异列表**并在界面上可见（哪一条协议、哪一项、文档说什么、实测是什么、何时发现）。

### 5.4 诚实声明（实现前必须确认）

**上游文档不一定是机器可读的稳定来源。** 若某上游文档是 JS 渲染页、或没有稳定锚点，
"文档巡检"可能退化为「**到期提醒 + 人工核对**」而无法自动比对。
**本 ADR 不承诺"全自动文档巡检"** —— 具体每条协议能自动到什么程度，须在实现时逐条确认。

## 6. 与 ADR-005（设置中心 IA）的关系

- ADR-005 曾定：「协议配置**取消一级导航** → 降为向导「高级」折叠区（专家模式才显眼）」，
  且 ADR-007 §4 进一步定为「降级为专家模式（**只读内置 + 有限覆盖**）」。
- **本 ADR 保留"取消一级导航"**（协议仍挂在「渠道」下，不新增顶级项），
  但**修正其形态**：它不是"被藏起来的可编辑表单"，而是
  **「只读的文档镜像 + 用户备注/覆盖层」**，且**带核对状态**。
- 与 Owner 已确认的设置导航简化（**模型 / 渠道 / 偏好** 三项，「用量」移入任务中心页签）不冲突：
  协议仍是「渠道」内的一个子页。

| 项 | 影响 |
|---|---|
| **新增维护责任** | 文档对齐需要有人维护（平台侧）。巡检能减轻，但**不能消除**（见 §5.4） |
| **不改数据架构** | 不改 ADR-003/004 的数据架构；供给池、候选、路由层均保留 |
| **现有页面** | `SettingsProtocols.tsx`（407 行 / 30 容器）需从"可增删改表单"改为"只读镜像 + 备注" —— **是一次真实的重写**，不是换位置 |
| **与 ADR-007 的实现差距** | ADR-007 只完成了"取消一级导航"这一步；本 ADR 把剩下的形态说清 |
| **不做的事** | 不做"用户从零手写协议"；不把文档当作事实来源；不承诺全自动文档巡检 |

## 10. 勘误（2026-10-10，本 ADR 自身的一处错误）

**§2 第 3 条与 §3 反例 1 的初版写法不准确**，原文为：

> 「模板照文档写 `Success`/`Failed`，官方枚举是 `completed`/`failed` ⇒ 该模板 100% 失败」

**问题**：`completed`/`failed` 并非"我们这条链路的官方枚举" —— 它来自**另一套/另一代接口的文档页**。
本项目实际轮询的端点（见 `pt_builtin_minimax_video.pollPath`）是 legacy 的
`GET /v1/query/video_generation`，其官方 OpenAPI 枚举为
**`Preparing | Queueing | Processing | Success | Fail`**。

**已按事实改写**（见上表）。**该错误由 AI 助手引入**：它采信了一份未经核实的取证台账并
写入本 ADR，属「宣称未验证」——正是本 ADR 与 `AGENTS.md §5.5` 要防的事。

**真实失效模式也不是"100% 失败"**：若终态值与实际不符，**失败无法被及时识别，任务会空转到轮询上限**
（`engine.go` 的 `maxPolls`），成功与失败在语义及重试策略上不同。

**教训**：**"文档"必须指明是哪一份、对应哪个端点** —— 只写"官方文档"不足以成为判据。
