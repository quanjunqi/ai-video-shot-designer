## 0. 我们做的是什么生意（后面一切的前提）

我们**不生产算力**，我们做的是**第三方 AI 算力的采购 + 编排 + 转售 + 治理**。三条硬约束：

| 约束 | 含义 |
|---|---|
| **两种钱必须分开** | 付给上游的（成本）vs 向客户收的（价格）。混在一起就永远算不出毛利 |
| **算力是商品** | 有单价、额度、并发上限、**失败率**、区域/合规限制。不是"一个 API 地址" |
| **上游会变** | 改字段、改状态值、涨价、下线 —— **必须能被检测**，而不是等客户投诉 |

> ⚠️ 最后一条不是理论。**实证**：MiniMax 视频模板的完成/失败值写成 `Success`/`Failed`，
> 而官方枚举是 `completed`/`failed` ⇒ 该模板下视频任务 **100% 不可用**，
> 且**成功与失败都检测不到**（空转到 6 分钟超时）。已修（PR #57/#58），但它证明了：
> **我们目前没有任何机制能发现这类问题**，只能靠偶然。

## 1. 模型算力：我们管理的到底是什么

### 1.1 四层资源模型（架构正确，产品面暴露错了）

```
供给来源（渠道）        能力（模型行）        产品面（逻辑模型）      调用方
──────────────────────────────────────────────────────────────────────────
官方直连  ─┐
中转站    ─┼─→ channel_models ──→ model_catalog ──→ logical_models ──→ 创作流
自建/云   ─┤     （供给池）          （目录）         （对外能力）
未来本地  ─┘
```

架构四层是对的（ADR-003 路由层 + ADR-004 供给池）。**问题在产品面**：

> **我们把四层全部暴露给了客户**（渠道/协议/模型/逻辑模型都在设置中心），
> 而客户**只该看到最上面那层**。

**实证**：`logical_models` 表**当前 0 行** —— **产品面是空的**。客户打开界面看到的是
「PearAPI GPT-Image 2」「nano-banana-2-lite」这类**上游商品名**，而不是「文生图（高质量）」
这类**他真正理解的能力名**。**这就是"黑盒感"的根因，不是"导航项太多"。**

### 1.2 不同供给的**成本形态不同**（计费设计的前提）

| 供给 | 计费单位 | 已知难点 |
|---|---|---|
| 官方直连（文本/图像） | 按 token（输入/输出/**缓存**分别计价） | 缓存命中价不同；流式与非流式不同 |
| 官方直连（视频） | **按秒 / 按分辨率档** | 时长可变，价格随档位跳变 |
| 中转站（PearAPI 等） | 按次 | **价格会变且不透明** |
| 自建 ComfyUI（云） | 按 GPU 时长 | 排队时间算不算？ |

⇒ **"价格"不能是一个字段，必须是一张可版本化的价格表**，且要能表达不同计费口径。

### 1.3 我们已知的价格数据是**错的**（实证）

- 手写的 `nano-banana-2-lite` 价格 = **¥2**，实际约 **¥0.06** ⇒ **33 倍误差**
- 而 `gateway_audit_logs` **已经有** `cost_amount`/`cost_currency`
  ⇒ **我们一直在记账，记的是错数**

> 这比"没记账"危险得多：进了客户账单 ⇒ 客户认为我们**多收钱**；
> 没进账单 ⇒ 我们**赔钱做**。两者都必须马上定位。

## 2. 如何接入：生命周期与"接入完成"的判据

### 2.1 生命周期（现在只有中间两小段）

```
① 发现（上游有什么） → ② 登记（渠道/凭据/协议）
                              ↓
                      ③ 验证  ← ★ 现在最弱的一环
                              ↓
                      ④ 启用（纳入路由候选）
                              ↓
                      ⑤ 监控（成功率/延迟/成本漂移/上游变更）
                              ↓
                      ⑥ 降级 / 恢复 / 下线
```

### 2.2 ★ **"接入完成"的判据必须是"真实生成成功"**

**现状**：`probeChannel` 返回 `{reachable, authOk, statusCode, detail}`。
**问题**：`authOk = true` 只证明**鉴权通过**，不证明**能出图**。

**实证**：MiniMax 视频模板 —— `authOk` 会是 `true`（Key 有效），但**任务永不成功**
（状态值不匹配）⇒ **坏的渠道会被标成"已接入"**。

| 能力类型 | 最小验证 | 判据 |
|---|---|---|
| 文生图 | 1 张 512×512 | 返回可访问 URL **且能取到字节** |
| 图生图 | 1 张参考图 → 1 张输出 | 同上 + 与参考的关联 |
| 视频 | ⚠️ **不可作为常规验证**（见 §2.2b 成本约束） | — |
| 文本 | 1 次短请求 | 非空文本 + token 计数 |

并把验证记录留档（"该渠道在何时被验证过"的证据）。

### 2.2b ⚠️ Owner 约束：**验证会花钱，视频不接受真实测试**

Owner 明确：*"验证的话会消耗钱。图片和文本我还可以接受，但视频的我接受不了真实测试。"*

⇒ **§2.2 的"一律跑一次真实生成"被推翻**。验证必须**按花费分级**：

| 级别 | 手段 | 花费 | 可自动 | 能证明 | **不能证明** |
|---|---|---|---|---|---|
| **L0 零成本** | 鉴权探测 + **轮询端点可达** + **响应契约核对**（字段名/状态枚举 vs 模板声明） | **0** | ✅ 可频繁 | 连接可用、契约未漂移 | **不能证明能出片** |
| **L1 低成本** | 文本/图片**真实最小生成** | 低 | ✅ | **端到端可用** | — |
| **L2 高成本** | 视频真实生成 | **高** | ❌ **必须人工显式授权** | 端到端可用 | — |

**推论一：契约核对（§2.4）不是锦上添花，而是视频类渠道唯一可行的日常检测手段。**

**推论二：界面必须诚实标注「证据等级」，不得把"鉴权通过"说成"已接入可用"**

```
🟢 已出片验证        （有真实产物证据：图片/文本，或管理员授权花过钱的视频）
🟡 连接与契约已验证，未验证出片  （L0 通过 —— 视频渠道的常态）
🔴 验证失败
```

与本仓库既有原则一致：**不做假承诺**（同 `queue-utils` 明确"不假装支持 pause/resume"）。

**推论三：验证消耗必须是独立的成本科目**

真实验证**是真实调用**，必须①记入审计与计费（否则成本对不上）②归到
**"渠道验证"科目**，与客户创作消耗**分开** —— 否则会污染客户的成本归因。

> ⇒ 计费设计的一个结论：**成本不只需要金额，还需要"归因维度"**（谁/为什么花的）。

**推论四：L2 的触发必须是"显式付费授权"**，且默认不发生；提示语要写明预估花费。

### 2.5 多来源供给：用户接入**自己的中转站**（Owner 补充约束）

Owner 指出：*"用户如果也有自己想接入的中转站而不是官方 api 呢，这种情况也需要考虑。"*

#### 四种供给归属（决定成本、价格、协议与责任）

| 供给归属 | 谁的 Key/账号 | **成本在谁** | 协议形态 | 我们靠什么收钱 |
|---|---|---|---|---|
| A 我们采购（供给池） | 我们的 | **我们** | 统一（内置协议） | 差价 / 服务费 |
| B 客户官方直连 | 客户的 | **客户自付** | 官方标准 | 平台 / 席位 / 服务费 |
| **C 客户自己的中转站** | 客户的 | **客户自付** | **各家不同（异构）** | 平台 / 席位 / 服务费 |
| D 客户自建（ComfyUI 云） | 客户的 | **客户自付** | 自定义工作流 | 平台 / 席位 / 服务费 |

**C 与 B 成本模型相同（都不进我们的成本），但协议风险完全不同。**
异构程度有实证：PearAPI 提交用复数 `/v1/videos/generations`、查询用**单数**
`/v1/video/generations/{id}`；MiniMax 一套接口 `completed/failed`、另一套
`succeeded/cancelled`。

#### 好消息：这个需求的底座已经建好

| 异构点 | 已有能力 | 来源 |
|---|---|---|
| 鉴权各家不同（`Bearer`/`x-api-key`/自定义头） | **`authHeader` + `authPrefix`**（数据驱动） | PR #50 |
| 路径 / 请求体各家不同 | **协议定义 + `{{占位符}}` 请求模板** | PR #51 / #56 |

⇒ **不需要让用户自己写协议**。绝大多数中转站是 **OpenAI 兼容**（PearAPI 即是），
用户从**内置协议形态**里选一个、只填 `base_url` + Key 即可；真正异构的由我们按需内置。

**为什么必须限制"用户自由写协议"**：任意 JSON/模板 ⇒ **无法验证、无法算成本、无法保障安全**。
（与 ADR-007 早前结论一致：用户自定义异构协议暂不支持。）

#### 由此新增的两个必须解决的问题

**① `base_url` 由用户填写 ⇒ SSRF 与"合法内网"冲突**

`netguard` 默认拒绝 loopback/私网/link-local ✅（含 `169.254.169.254`）。
**但用户自己的中转站可能就在其内网**（自部署场景尤甚）⇒ 默认拒绝会**挡住合法需求**。

⇒ 需要**显式、可审计、按渠道粒度**的"允许私网上游"开关（**不是全局一刀切**），
且开启必须留痕（谁、何时、为哪个渠道开启）。
（现状：`.env.example` 有 `EXECUTION_ALLOW_PRIVATE_UPSTREAM`，但其说明注释**错位**在
另一个变量上方，属既有缺陷。）

**② 成本字段必须能表达"客户自付"**

B/C/D 的 `cost_amount` **不能写 `0`**（会与"免费/无成本"混淆）⇒ 需明确语义，例如
`cost_bearer = platform | tenant`。否则**审计与对账都会算错**。

#### 对 §8 决策的影响

**使决策 1（商业模式）更可能是「混合」**：我们采购的走**差价**，
客户自带的走**平台/席位费**。因此决策 1 必须先定 —— 它决定计费字段与审计维度。

### 2.3 四种来源，流程与成本归属不同（详见 §2.5）

| 来源 | 谁接入 | 关键差别 |
|---|---|---|
| 官方直连 | 租户管理员填自己的 Key | 成本记在他头上 |
| 中转站 | **平台运营（我们）统一接** | 我们是买家；**池不能给客户看**（ADR-004） |
| 自建（ComfyUI 云） | 租户管理员填自己的端点 | 需校验端点可达 + 工作流可用（SSRF 防护已有：`netguard`） |

### 2.4 上游变更检测（**完全缺失**）

上游会静默变更：改状态值/字段名/错误码、涨价、下线模型。
**现在唯一的发现机制是"客户报障"**，不可接受。应有：

1. **可用性巡检**（定时最小生成，或至少定时鉴权）
2. **响应契约核对**（实测响应 vs 模板声明，不一致告警）—— 正好复用 ADR-007 注册表 + `requestTemplate`
3. **价格漂移检测**

## 3. 我们如何管理：**三个视角必须分开**（核心结论）

### 3.1 当前根本毛病

| 视角 | 他是谁 | 关心什么 | **不该看到** |
|---|---|---|---|
| **平台运营（我们）** | 我们自己 | 渠池健康度、成本、上游变更、协议库、计费规则 | — |
| **租户管理员（客户）** | 客户技术负责人 | **用哪个模型、花多少钱、谁能用** | **供给池、其它租户、我们付给上游多少钱** |
| **创作者** | 编剧/分镜 | 能生成什么、结果好不好 | **一切基础设施概念** |

设置中心 6 项（渠道/协议/模型/审计/通用/逻辑模型）**把三者平铺在一起**：
客户看到「协议配置」会懵（那是我们的实现细节），看到「渠道」会以为要自己维护上游（那是我们的活）。

### 3.2 三层职责边界

```
平台运营（我们的控制台，客户看不到）
  ├── 供给池：中转站/官方池、channel_models 同步、missing_since
  ├── 协议库：内置协议定义（代码注册表，ADR-007）
  ├── 成本与毛利：上游成本、价格表、对账
  └── 健康度：成功率/延迟/上游变更告警
        │ 只暴露"可用的逻辑模型"
        ▼
租户管理员（客户）
  ├── 我的模型：接哪些逻辑模型、绑定哪些渠道/Key
  ├── 我的额度：预算、配额、告警线
  ├── 我的成员：谁能用、能用多少
  └── 我的审计：谁在何时用了什么、花了多少
        │ 只暴露"能力名"
        ▼
创作者
  └── 直接创作（文生图/图生图/视频…），不接触基础设施概念
```

### 3.3 必须 Owner 拍板的**商业问题**

**成本对客户透明吗？**

| 模式 | 客户看到 | 我们的收入 | 需要的功能 |
|---|---|---|---|
| **A 代采购/托管** | 只看自己的额度消耗 | 差价（价格 − 成本） | 价格表、毛利看板、对账 |
| **B 透明转售** | 上游单价 + 我们的服务费 | 明示服务费 | 上游价与服务费分离展示 |
| **C 混合** | 默认 A，大客户可开 B | — | 两者都要 |

## 4.0 ⚠️ 商业模式修正（Owner 明确）—— 本章其余部分的前提被推翻

Owner 明确：*"我们没有想过走席位费和平台费，我们只是想收软件使用月卡，多少钱一个月的形式，
或者走私有化部署的交付，或者其他的利己方式的盈利模式。"*

⇒ **我们不是算力转售商（不收差价、不收席位费、不收平台费），而是软件授权商。**
§4.1–§4.3 的"三层价格结构（成本/价格/结算）"**仅适用于**"月卡含算力"或
"可选算力代采"这两种子情形，**不是主模式**。

### 4.0.1 两种主模式

| 模式 | 收入 | **算力成本谁承担** | 我们要计量什么 |
|---|---|---|---|
| **月卡订阅** | 每月固定 | **取决于月卡是否含算力** ⚠️ | 用量（**额度 / 公平使用 / 成本归因**，不是账单） |
| **私有化部署交付** | 一次性 + 可选年维保 | **客户**（他们自己买 Key/算力） | 用量（客户自己的审计 + 我们做产品改进，若允许上报） |

### 4.0.2 ★ 由此产生的**最大商业风险**

> **月卡若包含算力 ⇒ 固定月费 + 高额算力 = 单客户可能亏穿。**
> 一个低月费客户若跑大量视频，成本可达数倍于月费。**这不是定价技巧，是模式生死线。**

因此必须有（见 §8 决策 1b）：

- **月卡是否含算力**：① 不含（客户自备 Key，**成本风险为零**）② 含**硬额度**
  （每月 X 张图 / Y 分钟视频，超出限流或加购）③ 含"公平使用"软额度（靠监控）
- **超出策略**：限流 / 降级 / 加购 / 停服

**建议 ① 或 ②**：① 使我们的成本与客户用量**解耦**（最安全）；② 有竞争力但必须有**硬额度**。

### 4.0.3 对现有能力评价的修正：`quota` 是**止损线**，不是计费雏形

原先把它当作"计费雏形"是理解错误。它的真实价值：

1. 防止单客户吃掉全部算力
2. 识别滥用（异常用量告警）
3. **为月卡定价提供真实成本分布** —— 没有这个数据，定价只能拍脑袋

⚠️ 而它当前 **fail-open**（上游故障时放行）⇒ 在"月卡含算力"模式下等于**敞口无限**。
**该风险等级由 §7 的中等上调为高危。**

### 4.0.4 私有化部署带来的两个新问题（原分析缺失）

1. **授权/许可控制（license）**：客户部署在自己机房后如何保证授权？
   联网校验 / 离线授权文件 / 期限 / 节点数？注意：`workspace` 的"授权"是**权限**，
   与**许可（license）**不是一回事，不能混用同一套概念
2. **用量是否上报**：私有化部署我们看不到任何数据 ⇒ 无法做产品改进。
   是否提供"可选匿名上报"？（涉及客户信任，需明确开关与内容清单）

### 4.0.5 "其他利己方式"候选（基于**我们已有的资产**）

| 方向 | 我们已有什么 | 为什么可行 |
|---|---|---|
| **内容包**（风格库 / 镜头语言库 / 规则库 / 提示词模板） | 规则中心 + 镜头语言库 + 风格库**已在仓库** | 这些是**我们的知识产权**，**与软件授权可分开定价**，且与算力成本**完全解耦** |
| **定制协议接入** | ADR-007 注册表 + `{{占位符}}` 请求模板（PR #50/#51/#56） | 客户的中转站异构（§2.5）⇒ **帮他们接**是明确可收费的活 |
| **培训 / 认证 / 实施** | — | 私有化交付的天然附加项 |
| **算力代采**（可选增值，**非主模式**） | 供给池（ADR-004，未实现） | 仅当客户**不想自己买 Key** 时提供；此处才适用 §4.1 的差价模型 |
| **按"作品/导出"计量** | jobs + `gateway_audit_logs` 已有 | 比按席位更贴合创作工具，且与算力成本弱相关 |

**推荐优先"内容包"**：把我们的规则/镜头/风格知识变成可单独售卖的商品，
**与算力成本完全解耦** —— 最"利己"且不承担成本风险。

### 4.0.6 对 §8 决策的影响

- **决策 1（商业模式）重写**为三选：月卡 / 私有化交付 / 二者并行（+ 增值）
- **新增决策 1b：月卡是否含算力、含多少、超出怎么办** ← **当前最关键的一条**
- **新增决策 7：私有化部署的许可控制方式**（联网/离线、期限、节点数）
- **新增决策 8：私有化部署是否/如何上报用量**

## 4. 如何设计计费

### 4.1 三层结构（不可合并）

```
① 成本 Cost     付给上游的（按上游口径：token / 秒 / 次 / GPU 时）
② 价格 Price    向客户收的（按我们的口径，可含服务费/阶梯/套餐）
③ 结算 Billing  预扣 → 结算 → 差额返还（含失败、重试、超时）
```

### 4.2 计费的**六个必须**

| # | 必须 | 为什么 |
|---|---|---|
| 1 | **价格表可版本化** | 调价后**历史账单不能变**；每次调用记录 `price_version` |
| 2 | **幂等键 = job id** | 重试/超时重投**不得重复计费** |
| 3 | **预扣 + 结算** | 并发下防超支。现有 `quota` 是雏形，但它 **fail-open** ⇒ 上游故障时**放行**，可能超支 |
| 4 | **失败必须退款/不扣** | 上游失败、网关失败、超时 —— **三种分别处理**（超时的钱上游可能已收） |
| 5 | **对账能力** | 每日：上游实际账单 vs 我们记账，差额能算出并解释 |
| 6 | **异步任务计费时点** | 提交预扣、成功才扣、还是失败退？**产品决策** |

### 4.3 现状差距

| 项 | 现状 | 缺口 |
|---|---|---|
| 成本字段 | `gateway_audit_logs.cost_amount/cost_currency` ✅ | **数值不可信**（¥2 vs ¥0.06） |
| 价格表 | 无 | 价格散落在代码/手工 seed |
| 价格版本 | 无 | 历史账单无法保证不变 |
| 预扣 | `quota` 有额度检查（30s 缓存、fail-open） | 非"预扣-结算"两段式 |
| 退款 | 未见 | 失败/超时如何处理未定义 |
| 对账 | 无 | 无法证明收支相符 |

## 5. 如何做好审计

### 5.1 先分**用途**，再定字段（现在是一次性写全，未按用途组织）

| 用途 | 谁用 | 需要什么 | 保留期 | 冲突 |
|---|---|---|---|---|
| **合规留痕** | 法律/客户 | 谁、何时、调了什么上游、结果 | **长（年）** | 需脱敏 |
| **成本归因** | 租户管理员/我们 | 按项目/剧集/成员/模型聚合花费 | 中（1 年） | — |
| **故障定位** | 我们 | 完整请求/响应体、上游原始错误、trace | **短（30 天）** | 含敏感数据 |
| **质量评估** | 我们 | 渠道维度成功率、延迟、重试率 | 长（聚合值） | — |

> **核心矛盾**：故障定位要存**原始 payload**，合规要求**脱敏/最小化**。
> ⇒ **必须分级存储**：原始 payload 短期 + 元数据长期。

### 5.2 现状盘点（这一项我们做得**相对最好**）

`gateway_audit_logs` 已有：`request_id / workspace_id / project_id / episode_id / asset_id /
user_id / product / model_id / channel_id / provider_model / mode / request_payload /
response_payload / error_message / status / latency_ms / token_input / token_output /
token_cached / cost_amount / cost_currency / job_id / provider_task_id / created_at`

**维度覆盖足够** ✅（成本归因四要素 project/episode/user/model 齐备）。**缺口**：

1. **脱敏**：`request_payload`/`response_payload` 含 prompt 及可能敏感信息，**未见脱敏策略**
2. **保留期与归档**：未见
3. **聚合/查询**：`/api/v1/audit/logs` 只返回明细，**无渠道成功率、模型成本排行等聚合**
4. **导出**：出账/合规举证需要，未见
5. **写入可靠性**：ADR 要求"同步写入不丢失"，但崩溃/超时是否漏记**需验证**
6. **参数审计的可靠性刚建立**：`intent_payload` 曾被结果覆盖（已修，独立 `result_payload`）
   —— 在此之前"当初提交了什么参数"查不到

## 6. 三条"第一公里"

### 部署者（本地化部署）的第一件事

**不是**读文档，而是"**让系统跑起来，并知道跑对了**"。

实际踩过的 3 个坑，每个都该被自动捕获：

| 坑 | 现象 | 应该有 |
|---|---|---|
| `.env.local` 陈旧（合并前副本） | 修复合并后仍失败 | 启动时校验 `.env.local` 与 `.env.example` 的**键差异** |
| `ASSET_S3_ENDPOINT` 带 `http://` | `Endpoint url cannot have fully qualified paths.` | 自检指出"该值不能带 scheme" |
| MinIO 凭据与容器不一致（`minioadmin` vs `localminio`） | `The Access Key Id ... does not exist` | 自检**实际连一次对象存储** |

⇒ 需要 **`doctor` 一键自检**：中间件连通、迁移版本、对象存储、模型渠道可用性，
**每项给出"不对时怎么改"**。

### 管理员（租户管理员）的第一件事

**接通至少一个能真正出结果的模型**。现在：有页面但**无引导**；无"真实生成"验证
（`authOk` ≠ 能出图）；完成后**无"我现在能用了"的确认**。

⇒ 需要**接入向导**：选来源 → 填凭据 → **跑一次真实生成** → 显示"已接通，文生图可用"。

### 创作者的第一件事

**直接创作**。这一环目前最好（智能创作工作台已在 `develop`）—— 但**前提是**
管理员已接通模型、且 `logical_models` 有数据（**现在是 0 行**）。
